# Module 0.5: The Java Build Process

**Objective:** Understand the complete Java build pipeline — from `.java` source files to a deployable `.jar` artifact — step by step.

---

## 0.5.1 The Java Build Pipeline

Every Java project follows this pipeline:

```
Source Code    →    Compilation    →    Object Files    →    Packaging    →    Artifact
(.java)              (javac)           (.class)             (jar/war)        (.jar/.war)
```

Let's walk through each step with a real project.

---

## 0.5.2 Step-by-Step Example — Building a Spring Boot Microservice

Imagine you're at a company building an order management service. The developers have written these files:

```
order-service/
├── src/main/java/com/company/order/
│   ├── OrderController.java        ← Handles HTTP requests
│   ├── OrderService.java           ← Business logic
│   └── OrderRepository.java        ← Database access
├── src/main/resources/
│   └── application.properties      ← Configuration
├── src/test/java/com/company/order/
│   └── OrderServiceTest.java       ← Unit tests
└── pom.xml                         ← Maven configuration
```

### Step 1: Source Code (.java files)

These are the files developers write. They are plain text — you can open them in any text editor.

```java
// OrderController.java — handles HTTP requests
@RestController
@RequestMapping("/orders")
public class OrderController {

    @Autowired
    private OrderService orderService;

    @PostMapping
    public Order createOrder(@RequestBody Order order) {
        return orderService.createOrder(order);
    }

    @GetMapping("/{id}")
    public Order getOrder(@PathVariable Long id) {
        return orderService.getOrder(id);
    }
}
```

```java
// OrderService.java — business logic
@Service
public class OrderService {

    @Autowired
    private OrderRepository orderRepository;

    public Order createOrder(Order order) {
        order.setStatus("CREATED");
        order.setCreatedAt(LocalDateTime.now());
        return orderRepository.save(order);
    }

    public Order getOrder(Long id) {
        return orderRepository.findById(id)
            .orElseThrow(() -> new RuntimeException("Order not found"));
    }
}
```

```java
// OrderRepository.java — database access
@Repository
public interface OrderRepository extends JpaRepository<Order, Long> {
    List<Order> findByStatus(String status);
}
```

At this point, these are just text files. The computer cannot execute them.

---

### Step 2: Compilation (.java → .class)

The Java compiler (`javac`) converts each `.java` file into a `.class` file containing **bytecode** — instructions that the Java Virtual Machine (JVM) can understand.

```
javac (compiler)
─────────────────────────────────────────────────────────
OrderController.java    ──►    OrderController.class
OrderService.java       ──►    OrderService.class
OrderRepository.java    ──►    OrderRepository.class
```

**What happens internally:**

```bash
# When Maven runs: mvn compile
# It calls javac behind the scenes:

javac -cp dependencies/*.jar \
  src/main/java/com/company/order/OrderController.java \
  src/main/java/com/company/order/OrderService.java \
  src/main/java/com/company/order/OrderRepository.java \
  -d target/classes/

# Output:
target/classes/
└── com/company/order/
    ├── OrderController.class     ← bytecode (not human-readable)
    ├── OrderService.class        ← bytecode
    └── OrderRepository.class     ← bytecode
```

**What does a .class file look like?**

```
$ hexdump -C OrderController.class | head -3
00000000  ca fe ba be 00 00 00 3d  00 5a 0a 00 02 00 03 07  |.......=.Z......|
00000010  00 04 0c 00 05 00 06 01  00 10 6a 61 76 61 2f 6c  |..........java/l|
00000020  61 6e 67 2f 4f 62 6a 65  63 74 01 00 06 3c 69 6e  |ang/Object...<in|
```

It starts with `CA FE BA BE` — the magic bytes that identify every Java class file. This is not human-readable — it's bytecode for the JVM.

---

### Step 3: Testing

After compilation, Maven runs the unit tests to verify the code works:

```bash
# Maven runs: mvn test
# Which executes:

java -cp target/classes:target/test-classes:dependencies/*.jar \
  org.junit.runner.JUnitCore com.company.order.OrderServiceTest

# Output:
# Tests run: 5, Failures: 0, Errors: 0, Skipped: 0
# BUILD SUCCESS
```

```java
// OrderServiceTest.java
@SpringBootTest
class OrderServiceTest {

    @Autowired
    private OrderService orderService;

    @Test
    void testCreateOrder() {
        Order order = new Order();
        order.setProduct("Laptop");
        order.setQuantity(1);

        Order created = orderService.createOrder(order);

        assertEquals("CREATED", created.getStatus());
        assertNotNull(created.getCreatedAt());
    }
}
```

If any test fails, the build stops. The artifact is not created. This prevents broken code from reaching QA or production.

---

### Step 4: Packaging (.class → .jar)

After compilation and testing pass, Maven bundles everything into a single JAR file:

```
target/classes/                              target/
├── com/company/order/                       └── order-service-1.0.jar
│   ├── OrderController.class                    │
│   ├── OrderService.class        ────────►      ├── com/company/order/*.class
│   └── OrderRepository.class                    ├── application.properties
├── application.properties                       ├── META-INF/MANIFEST.MF
└── (30+ dependency JARs)                        └── BOOT-INF/lib/*.jar
                                                     (all dependencies bundled)
```

**The final artifact:**

```bash
$ ls -lh target/order-service-1.0.jar
-rw-r--r-- 1 user user 45M  order-service-1.0.jar

# That single 45MB JAR contains:
# - Your compiled .class files
# - application.properties
# - All 30+ dependency JARs (Spring, Hibernate, Tomcat, etc.)
# - Embedded Tomcat web server
```

This single file is the **artifact** — the deliverable that QA tests and Operations deploys.

---

### Step 5: Running the Artifact

```bash
# Run the JAR — the entire application starts
java -jar target/order-service-1.0.jar

# Output:
#   .   ____          _            __ _ _
#  /\\ / ___'_ __ _ _(_)_ __  __ _ \ \ \ \
# ( ( )\___ | '_ | '_| | '_ \/ _` | \ \ \ \
#  \\/  ___)| |_)| | | | | || (_| |  ) ) ) )
#   '  |____| .__|_| |_|_| |_\__, | / / / /
#  =========|_|==============|___/=/_/_/_/
#  :: Spring Boot ::                (v3.2.0)
#
# Started OrderServiceApplication in 3.2 seconds
# Tomcat started on port 8080
```

The application is now running. Customers can access it at `http://server:8080/orders`.

## 0.5.3 The Complete Pipeline — Visual Summary

```
Developer writes code
        │
        ▼
┌─────────────────┐
│  .java files    │  ← Source code (human-readable)
│  (3 files)      │
└────────┬────────┘
         │  javac (compilation)
         ▼
┌─────────────────┐
│  .class files   │  ← Bytecode (machine-readable)
│  (3 files)      │
└────────┬────────┘
         │  JUnit (testing)
         ▼
┌─────────────────┐
│  Test Results   │  ← Pass or Fail
│  5 tests passed │
└────────┬────────┘
         │  jar (packaging)
         ▼
┌─────────────────┐
│  .jar file      │  ← Artifact (single deployable file)
│  (1 file, 45MB) │
└────────┬────────┘
         │  deploy
         ▼
┌─────────────────┐
│  Production     │  ← Running application
│  Server         │
└─────────────────┘
```

**With Maven, this entire pipeline is one command:**

```bash
mvn clean package
# clean   → delete old build output
# compile → .java → .class
# test    → run unit tests
# package → .class → .jar
```

## 0.5.4 Real Company Example — What Happens at Scale

At a company building a Spring Boot microservice with:
- 150 Java source files
- 40 external dependencies (Spring, Hibernate, Jackson, etc.)
- 300 unit tests

**Build output:**

```
$ mvn clean package

[INFO] --- maven-compiler-plugin:3.12.1:compile ---
[INFO] Compiling 150 source files to target/classes
[INFO]
[INFO] --- maven-surefire-plugin:3.2.3:test ---
[INFO] Tests run: 300, Failures: 0, Errors: 0, Skipped: 0
[INFO]
[INFO] --- maven-jar-plugin:3.3.0:jar ---
[INFO] Building jar: target/order-service-1.0.jar
[INFO]
[INFO] BUILD SUCCESS
[INFO] Total time: 45 seconds
```

**Result:** 150 `.java` files + 40 dependencies → 1 single `order-service-1.0.jar` (45MB)

That single JAR contains hundreds of `.class` files. QA tests this JAR. Operations deploys this JAR. Customers use the application running from this JAR.

## 0.5.5 Why This Matters for DevOps Engineers

As a DevOps engineer, you need to understand this pipeline because:

1. **CI/CD pipelines automate it** — Jenkins/GitLab CI runs `mvn clean package`
2. **Build failures happen at each step** — you need to know WHERE it failed:
   - Compilation error → developer wrote bad code
   - Test failure → code broke existing functionality
   - Packaging error → dependency conflict or configuration issue
3. **Artifacts are what you deploy** — you deploy JARs, not source code
4. **Artifact versioning matters** — `order-service-1.0.jar` vs `order-service-2.0.jar`

```
Common build failure messages and what they mean:

"Compilation failure"
  → A .java file has a syntax error or missing import
  → Fix: Developer needs to fix the code

"Tests run: 10, Failures: 2"
  → Code compiles but 2 tests failed
  → Fix: Developer needs to fix the failing tests

"Could not resolve dependencies"
  → Maven can't download a required library
  → Fix: Check pom.xml, check network, check repository URL

"OutOfMemoryError during build"
  → Build needs more RAM
  → Fix: export MAVEN_OPTS="-Xmx1024m"
```

## 0.5.6 Hands-On Exercise

```bash
# 1. Create a multi-file Java project manually (no Maven)
mkdir -p /tmp/java-build-demo/src/com/demo
cd /tmp/java-build-demo

# Create two Java files
cat > src/com/demo/Calculator.java << 'EOF'
package com.demo;
public class Calculator {
    public int add(int a, int b) { return a + b; }
    public int multiply(int a, int b) { return a * b; }
}
EOF

cat > src/com/demo/Main.java << 'EOF'
package com.demo;
public class Main {
    public static void main(String[] args) {
        Calculator calc = new Calculator();
        System.out.println("2 + 3 = " + calc.add(2, 3));
        System.out.println("4 x 5 = " + calc.multiply(4, 5));
    }
}
EOF

# 2. Compile manually
mkdir -p target/classes
javac -d target/classes src/com/demo/*.java
ls target/classes/com/demo/    # See the .class files

# 3. Run the compiled code
java -cp target/classes com.demo.Main

# 4. Package into a JAR
jar cfe target/calculator.jar com.demo.Main -C target/classes .
ls -la target/calculator.jar

# 5. Run the JAR
java -jar target/calculator.jar

# 6. Clean up
rm -rf /tmp/java-build-demo

# Notice how many manual steps this took for just 2 files.
# Now imagine 150 files with 40 dependencies.
# That's why Maven exists.
```

# Module 3: EC2 - Elastic Compute Cloud

## 3.1 What is EC2?

EC2 provides resizable virtual servers (instances) in the cloud. Instead of buying physical servers, you rent compute capacity by the hour/second.

### Real-World Analogy
- **Physical server** = Buying a house (large upfront cost, you maintain everything)
- **EC2 instance** = Renting an apartment (pay monthly, landlord handles infrastructure)

### EC2 Components

```
┌──────────────────────────────────────────────┐
│                EC2 Instance                   │
│                                               │
│  ┌─────────────┐  ┌──────────────────────┐   │
```

### How to Choose an Instance Type

```
What is your workload?
    │
    ├── Unpredictable / bursty traffic ──────▶ t3 / t4g (General Purpose)
    ├── Steady web/app server ───────────────▶ m5 / m6i (General Purpose)
    ├── CPU-heavy (encoding, batch) ─────────▶ c5 / c6i (Compute Optimized)
    ├── Large database / caching ────────────▶ r5 / r6i (Memory Optimized)
    ├── ML training / GPU rendering ─────────▶ p4 / g5 (Accelerated Computing)
    ├── ML inference ────────────────────────▶ inf2 (Accelerated Computing)
    └── High disk I/O (NoSQL, logs) ─────────▶ i3 / i4i (Storage Optimized)
```

## 3.4 Key Pairs

Key pairs provide SSH access to Linux instances. AWS stores the public key; you download and keep the private key.

### Manual Steps via AWS Console: Create Key Pair

1. Go to **EC2 → Key Pairs → Create key pair**
2. Name: `my-app-key`
3. Key pair type: `RSA`
4. Private key file format: `.pem` (for Linux/Mac) or `.ppk` (for PuTTY on Windows)
5. Click **Create key pair** — the `.pem` file downloads automatically
6. Move the file to a safe location and set permissions:
   ```bash
   mv ~/Downloads/my-app-key.pem ~/.ssh/
   chmod 400 ~/.ssh/my-app-key.pem
   ```

⚠️ You can only download the private key ONCE at creation time. If you lose it, you must create a new key pair.

### Create a Key Pair (CLI)

```bash
aws ec2 create-key-pair \
  --key-name my-app-key \
  --query 'KeyMaterial' \
  --output text > my-app-key.pem

# Set correct permissions (required for SSH)
chmod 400 my-app-key.pem
```

**Command Breakdown:**
- `create-key-pair` → Generates RSA key pair
- `--key-name` → Name stored in AWS
- `--query 'KeyMaterial'` → Extracts only the private key
- `> my-app-key.pem` → Saves to file
- `chmod 400` → Read-only for owner (SSH requires this)

### List Key Pairs


## 3.5 Security Groups

Security groups act as virtual firewalls controlling inbound/outbound traffic for EC2 instances.

### Manual Steps via AWS Console: Create Security Group

1. Go to **EC2 → Security Groups → Create security group**
2. Name: `web-server-sg`
3. Description: `Allow HTTP, HTTPS, and SSH`
4. VPC: select your VPC
5. **Inbound rules** → Add rules:
   - Type: `SSH`, Port: `22`, Source: `My IP` (auto-fills your IP)
   - Type: `HTTP`, Port: `80`, Source: `Anywhere-IPv4` (0.0.0.0/0)
   - Type: `HTTPS`, Port: `443`, Source: `Anywhere-IPv4` (0.0.0.0/0)
6. **Outbound rules**: leave default (all traffic allowed out)
7. Click **Create security group**

### Create a Security Group (CLI)

```bash
aws ec2 create-security-group \
  --group-name web-server-sg \
  --description "Allow HTTP, HTTPS, and SSH"
```

**Expected Output:**
```json
{
    "GroupId": "sg-0a1b2c3d4e5f67890"
}
```

### Add Inbound Rules

```bash
# Allow SSH (port 22) from your IP only
aws ec2 authorize-security-group-ingress \
  --group-id sg-0a1b2c3d4e5f67890 \
  --protocol tcp \
  --port 22 \
  --cidr 203.0.113.50/32

# Allow HTTP (port 80) from anywhere
aws ec2 authorize-security-group-ingress \
  --group-id sg-0a1b2c3d4e5f67890 \
  --protocol tcp \
  --port 80 \
  --cidr 0.0.0.0/0

# Allow HTTPS (port 443) from anywhere
aws ec2 authorize-security-group-ingress \
  --group-id sg-0a1b2c3d4e5f67890 \
  --protocol tcp \
  --port 443 \
  --cidr 0.0.0.0/0
```

### View Security Group Rules

```bash
aws ec2 describe-security-groups \
  --group-ids sg-0a1b2c3d4e5f67890 \
  --query 'SecurityGroups[0].IpPermissions' \
  --output table
```

## 3.6 Launch an EC2 Instance

### Manual Steps via AWS Console: Launch an EC2 Instance

1. Go to **EC2 → Instances → Launch instances**
2. **Name**: `WebServer`
3. **AMI**: Select `Amazon Linux 2023` (Free Tier eligible)
4. **Instance type**: `t3.micro` (Free Tier eligible)
5. **Key pair**: Select `my-app-key` (or create a new one)
6. **Network settings** → Click **Edit**:
   - VPC: select your VPC
   - Subnet: select a public subnet
   - Auto-assign public IP: `Enable`
   - Security group: select `web-server-sg`
7. **Configure storage**: 8 GiB gp3 (default, Free Tier eligible)
8. **Advanced details** (optional):
   - IAM instance profile: select a role if needed
   - User data: paste your bootstrap script
9. **Number of instances**: 1
10. Click **Launch instance**
11. Go to **Instances** → wait for Instance state = `Running`
12. Select the instance → copy the **Public IPv4 address**
13. Connect via SSH:
    ```bash
    ssh -i my-app-key.pem ec2-user@<PUBLIC_IP>
    ```

### Launch via CLI

```bash
aws ec2 run-instances \
  --image-id ami-0c55b159cbfafe1f0 \
  --instance-type t3.micro \
  --key-name my-app-key \
  --security-group-ids sg-0a1b2c3d4e5f67890 \
  --count 1 \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=WebServer},{Key=Environment,Value=dev}]'
```

**Command Breakdown:**
| Flag | Meaning |
|------|---------|
| `--image-id` | AMI to use (OS template) |
| `--instance-type` | Hardware specs |
| `--key-name` | SSH key pair |
| `--security-group-ids` | Firewall rules |
| `--count 1` | Number of instances |
| `--tag-specifications` | Name and metadata tags |

## 3.8 EBS Volumes (Elastic Block Store)

EBS provides persistent block storage for EC2 instances. Think of EBS as a virtual hard drive that you can attach to any EC2 instance in the same Availability Zone.

### Manual Steps via AWS Console: Create, Attach, and Resize EBS

**Create a new EBS volume:**
1. Go to **EC2 → Volumes → Create volume**
2. Volume type: `gp3` (General Purpose SSD)
3. Size: `20` GiB
4. Availability Zone: **must match your EC2 instance's AZ** (e.g., `us-east-1a`)
5. Add tag: Name = `DataVolume`
6. Click **Create volume**

**Attach the volume to an instance:**
1. Select the volume → **Actions → Attach volume**
2. Instance: select your EC2 instance
3. Device name: `/dev/xvdf` (or let AWS auto-assign)
4. Click **Attach volume**
5. SSH into the instance and format/mount (see CLI steps below)

**Resize an existing volume:**
1. Select the volume → **Actions → Modify volume**
2. Change size from `20` to `50` GiB
3. Click **Modify** → **Yes** to confirm
4. Wait for state to change from `modifying` to `optimizing` to `completed`
5. SSH into the instance and extend the filesystem:
   ```bash
   # Check that OS sees the new size
   lsblk
   # Extend the filesystem
   sudo resize2fs /dev/xvdf    # for ext4
   sudo xfs_growfs /data        # for xfs
   # Verify
   df -h /data
   ```

**Create a snapshot (backup):**
1. Select the volume → **Actions → Create snapshot**
2. Description: `Data volume backup 2024-01-15`
3. Add tag: Name = `DataBackup`
4. Click **Create snapshot**

**Restore from snapshot:**
1. Go to **EC2 → Snapshots** → select the snapshot
2. **Actions → Create volume from snapshot**
3. Select AZ, size, type → **Create volume**
4. Attach the new volume to your instance

### EBS Volume Types

| Type | Name | IOPS | Use Case |
|------|------|------|----------|
| `gp3` | General Purpose SSD | 3,000-16,000 | Boot volumes, dev/test |
| `gp2` | General Purpose SSD | Up to 16,000 | Legacy default |
| `io2` | Provisioned IOPS SSD | Up to 256,000 | Databases |
| `st1` | Throughput HDD | 500 | Big data, log processing |
| `sc1` | Cold HDD | 250 | Infrequent access |

### Inspect a New Disk Before Formatting

Before formatting a new EBS volume, check if it already has a filesystem:

```bash
# SSH into instance, then:

# Check all block devices
lsblk
# Output:
# NAME    MAJ:MIN RM SIZE RO TYPE MOUNTPOINT
# xvda    202:0    0   8G  0 disk
# └─xvda1 202:1    0   8G  0 part /
# xvdf    202:80   0  20G  0 disk          <-- new volume, no mountpoint

# Check if the volume has a filesystem (IMPORTANT: do this before formatting)
sudo file -s /dev/xvdf
# Output if NO filesystem (raw disk):
#   /dev/xvdf: data
# Output if filesystem EXISTS:
#   /dev/xvdf: Linux rev 1.0 ext4 filesystem data
```

**`file -s`** reads the superblock of the device to detect existing filesystems. If it says `data`, the disk is empty and safe to format. If it shows a filesystem type, formatting will destroy existing data.

### Format and Mount (on the instance)

```bash
# --- Option A: Format with ext4 (recommended for most use cases) ---
sudo mkfs -t ext4 /dev/xvdf

# --- Option B: Format with ext3 using mke2fs (journal-based) ---
sudo mke2fs -j /dev/xvdf
# -j flag creates an ext3 filesystem with journaling
# Journaling helps recover data after crashes

# Create mount point and mount
sudo mkdir /data
sudo mount /dev/xvdf /data

# Make persistent across reboots
echo '/dev/xvdf /data ext4 defaults,nofail 0 2' | sudo tee -a /etc/fstab

# Verify
df -h /data
# Output:
# Filesystem      Size  Used Avail Use% Mounted on
# /dev/xvdf        20G   45M   19G   1% /data

# Verify with lsblk (now shows mountpoint)
lsblk
# Output:
# NAME    MAJ:MIN RM SIZE RO TYPE MOUNTPOINT
# xvda    202:0    0   8G  0 disk
# └─xvda1 202:1    0   8G  0 part /
# xvdf    202:80   0  20G  0 disk /data     <-- mounted
```

### How to Increase EBS Volume Size

You can resize an EBS volume without downtime. This is a two-step process: resize in AWS, then extend the filesystem on Linux.

**Step 1: Modify the volume size in AWS**

```bash
# Check current volume size
aws ec2 describe-volumes \
  --volume-ids vol-0abcd1234efgh5678 \
  --query 'Volumes[0].{Size:Size,State:State,Type:VolumeType}' \
  --output table

# Expected Output:
# ---------------------------------
# |       DescribeVolumes          |
# +-------+-------+---------------+
# | Size  | State |    Type       |
# +-------+-------+---------------+
# |  20   | in-use|    gp3        |
# +-------+-------+---------------+

# Increase from 20GB to 50GB (can only increase, never decrease)
aws ec2 modify-volume \
  --volume-id vol-0abcd1234efgh5678 \
  --size 50

# Wait for modification to complete
aws ec2 describe-volumes-modifications \
  --volume-ids vol-0abcd1234efgh5678 \
  --query 'VolumesModifications[0].{State:ModificationState,Progress:Progress}'

# Expected Output:
# { "State": "optimizing", "Progress": 100 }
```

**Step 2: Extend the filesystem on the Linux instance**

```bash
# SSH into the instance

# Check current disk — lsblk shows new size, but filesystem hasn't expanded yet
lsblk
# Output:
# NAME    MAJ:MIN RM SIZE RO TYPE MOUNTPOINT
# xvdf    202:80   0  50G  0 disk /data     <-- disk is 50G

df -h /data
# Output:
# Filesystem      Size  Used Avail Use% Mounted on
# /dev/xvdf        20G   45M   19G   1% /data   <-- filesystem still 20G!

# For a non-partitioned volume (xvdf with no partitions):
# Resize the ext4 filesystem to use all available space
sudo resize2fs /dev/xvdf

# For a partitioned volume (e.g., xvda1):
# First grow the partition, then resize the filesystem
sudo growpart /dev/xvda 1
sudo resize2fs /dev/xvda1

# For XFS filesystems (Amazon Linux 2023 root volume):
sudo xfs_growfs /data

# Verify the filesystem now uses the full 50GB
df -h /data
# Output:
# Filesystem      Size  Used Avail Use% Mounted on
# /dev/xvdf        49G   52M   47G   1% /data   <-- expanded!
```

**Summary of EBS resize steps:**
1. `aws ec2 modify-volume` — increase size in AWS
2. `lsblk` — confirm OS sees the new size
3. `sudo growpart` — expand partition (if partitioned)
4. `sudo resize2fs` or `sudo xfs_growfs` — expand filesystem
5. `df -h` — verify

## 3.9 Elastic IP

An Elastic IP is a static public IPv4 address.

```bash
# Allocate an Elastic IP
aws ec2 allocate-address --domain vpc
```

**Expected Output:**
```json
{
    "PublicIp": "54.123.45.67",
    "AllocationId": "eipalloc-0abcd1234efgh5678",
    "Domain": "vpc"
}
```

```bash
# Associate with instance
aws ec2 associate-address \
  --instance-id i-0abcd1234efgh5678 \
  --allocation-id eipalloc-0abcd1234efgh5678

# Release (when done — unattached EIPs cost money!)
aws ec2 disassociate-address --association-id eipassoc-0abcd1234
aws ec2 release-address --allocation-id eipalloc-0abcd1234efgh5678
```

⚠️ **Elastic IPs are free when attached to a running instance. You're charged when they're allocated but NOT attached.**

## 3.10 EC2 Instance Lifecycle and Billing

### Instance States

```
┌──────────┐    ┌──────────┐    ┌──────────┐
│ Pending  │───▶│ Running  │───▶│ Stopping │
└──────────┘    └────┬─────┘    └────┬─────┘
                     │               │
                     │          ┌────▼─────┐    ┌────────────┐
                     │          │ Stopped  │───▶│ Terminated │
                     │          └──────────┘    └────────────┘
                     │
                     └──────────────────────────▶ Terminated
```

### Billing Per State

Understanding when you pay is essential to avoid unexpected charges:

| State | Compute Billing | EBS Billing | Elastic IP Billing | Notes |
|-------|----------------|-------------|-------------------|-------|
| **Pending** | ❌ No | ✅ Yes | N/A | Instance is booting |
| **Running** | ✅ Yes (per second, min 60s) | ✅ Yes | ❌ Free (attached) | Full charges apply |
| **Stopping** | ❌ No | ✅ Yes | ❌ Free | Transitional state |
| **Stopped** | ❌ No | ✅ Yes | ✅ Charged (if allocated) | EBS volumes still cost money |
| **Shutting-down** | ❌ No | ❌ No | ✅ Charged (if unattached) | Transitional state |
| **Terminated** | ❌ No | ❌ No (root EBS deleted) | ✅ Charged (if not released) | Instance is gone |

**Key billing facts:**
- Compute billing starts when state = `running`, billed per second with a 60-second minimum
- EBS volumes are billed as long as they exist, regardless of instance state
- A stopped instance still costs money for its EBS volumes
- Elastic IPs cost money when allocated but NOT attached to a running instance
- Data transfer out is billed; data transfer in is free

## 3.12 Elastic Load Balancer (ELB)

A load balancer distributes incoming traffic across multiple EC2 instances to ensure no single instance is overwhelmed.

### ELB Types

```
┌─────────────────────────────────────────────────────────────────────┐
│                    AWS Load Balancer Types                          │
├──────────────────┬──────────────────────────────────────────────────┤
│  ALB             │  Layer 7 (HTTP/HTTPS)                           │
│  (Application)   │  Path-based routing, host-based routing         │
│                  │  Best for: web apps, microservices, REST APIs   │
├──────────────────┼──────────────────────────────────────────────────┤
│  NLB             │  Layer 4 (TCP/UDP)                              │
│  (Network)       │  Ultra-low latency, millions of requests/sec   │
│                  │  Best for: gaming, IoT, real-time streaming     │
├──────────────────┼──────────────────────────────────────────────────┤
│  GLB             │  Layer 3 (IP)                                   │
│  (Gateway)       │  Third-party virtual appliances                 │
│                  │  Best for: firewalls, IDS/IPS, deep inspection  │
├──────────────────┼──────────────────────────────────────────────────┤
│  CLB             │  Layer 4/7 (Legacy)                             │
│  (Classic)       │  DEPRECATED — do not use for new deployments    │
└──────────────────┴──────────────────────────────────────────────────┘
```

### How Load Balancing Works — Round Robin Method

By default, ALB uses a **round robin** algorithm to distribute requests across healthy targets:

```
Client Request #1 ──▶ ALB ──▶ Instance A
Client Request #2 ──▶ ALB ──▶ Instance B
Client Request #3 ──▶ ALB ──▶ Instance C
Client Request #4 ──▶ ALB ──▶ Instance A  (cycles back)
Client Request #5 ──▶ ALB ──▶ Instance B
Client Request #6 ──▶ ALB ──▶ Instance C
...

Round Robin: Each instance gets requests in turn, one after another.
If an instance fails its health check, ALB removes it from rotation.
```

ALB also supports **least outstanding requests** routing, which sends traffic to the instance with the fewest in-flight requests (better for uneven workloads).

### Manual Steps: Create an Application Load Balancer (ALB)

**Step 1: Create a Security Group for the ALB**

```bash
ALB_SG=$(aws ec2 create-security-group \
  --group-name alb-sg \
  --description "ALB - allow HTTP and HTTPS from internet" \
  --vpc-id vpc-0abcd1234 \
  --query 'GroupId' --output text)

# Allow HTTP from anywhere
aws ec2 authorize-security-group-ingress \
  --group-id $ALB_SG --protocol tcp --port 80 --cidr 0.0.0.0/0

# Allow HTTPS from anywhere
aws ec2 authorize-security-group-ingress \
  --group-id $ALB_SG --protocol tcp --port 443 --cidr 0.0.0.0/0

echo "ALB Security Group: $ALB_SG"
```

**Step 2: Create the ALB**

```bash
# ALB must be in at least 2 subnets (different AZs)
ALB_ARN=$(aws elbv2 create-load-balancer \
  --name my-web-alb \
  --subnets subnet-aaa111 subnet-bbb222 \
  --security-groups $ALB_SG \
  --scheme internet-facing \
  --type application \
  --query 'LoadBalancers[0].LoadBalancerArn' \
  --output text)

echo "ALB ARN: $ALB_ARN"
```

**Expected Output:**
```
ALB ARN: arn:aws:elasticloadbalancing:us-east-1:123456789012:loadbalancer/app/my-web-alb/abc123def456
```

**Step 3: Create a Target Group**

A target group defines where the ALB sends traffic and how it checks instance health.

```bash
TG_ARN=$(aws elbv2 create-target-group \
  --name web-servers-tg \
  --protocol HTTP \
  --port 80 \
  --vpc-id vpc-0abcd1234 \
  --health-check-path /health \
  --health-check-interval-seconds 30 \
  --healthy-threshold-count 2 \
  --unhealthy-threshold-count 3 \
  --query 'TargetGroups[0].TargetGroupArn' \
  --output text)

echo "Target Group ARN: $TG_ARN"
```

**Step 4: Register EC2 Instances as Targets**

```bash
# Register two instances
aws elbv2 register-targets \
  --target-group-arn $TG_ARN \
  --targets Id=i-instance1 Id=i-instance2

# Check target health
aws elbv2 describe-target-health \
  --target-group-arn $TG_ARN \
  --output table
```

**Expected Output:**
```
---------------------------------------------------
|            DescribeTargetHealth                  |
+----------------+----------+---------------------+
|    Target      |  State   |    Description       |
+----------------+----------+---------------------+
| i-instance1    | healthy  |                      |
| i-instance2    | healthy  |                      |
+----------------+----------+---------------------+
```

**Step 5: Create a Listener**

The listener checks for incoming connections and forwards them to the target group.

```bash
aws elbv2 create-listener \
  --load-balancer-arn $ALB_ARN \
  --protocol HTTP \
  --port 80 \
  --default-actions Type=forward,TargetGroupArn=$TG_ARN
```

**Step 6: Get the ALB DNS Name and Test**

```bash
ALB_DNS=$(aws elbv2 describe-load-balancers \
  --load-balancer-arns $ALB_ARN \
  --query 'LoadBalancers[0].DNSName' \
  --output text)

echo "Access your app at: http://$ALB_DNS"

# Test — each request may go to a different instance (round robin)
curl http://$ALB_DNS
curl http://$ALB_DNS
curl http://$ALB_DNS
```

### Manual Steps via AWS Console

1. Go to **EC2 → Load Balancers → Create Load Balancer**
2. Choose **Application Load Balancer**
3. Name: `my-web-alb`, Scheme: `Internet-facing`
4. Select at least 2 Availability Zones and their public subnets
5. Select or create a security group allowing HTTP/HTTPS
6. Create a **Target Group**: name it, set protocol HTTP, port 80, health check path `/health`

8. Create a **Listener** on port 80 forwarding to the target group
9. Review and create
10. Copy the DNS name and test in your browser

### Delete ALB Resources

```bash

LISTENER_ARN=$(aws elbv2 describe-listeners \
```

## 3.13 Auto Scaling Group (ASG)

An Auto Scaling Group automatically adjusts the number of EC2 instances based on demand. It launches new instances when load increases and terminates them when load decreases.

### How ASG Works

```
                    ┌─────────────────────────────────────┐
                    │        Auto Scaling Group            │
                    │                                      │
  Traffic ──▶ ALB ──┤  Min: 2    Desired: 2    Max: 6    │
  increases         │                                      │
                    │  ┌────┐ ┌────┐                      │
                    │  │ i-1│ │ i-2│  ← normal load       │
                    │  └────┘ └────┘                      │
                    │                                      │
  High CPU!         │  ┌────┐ ┌────┐ ┌────┐ ┌────┐      │
  Scale out ──▶     │  │ i-1│ │ i-2│ │ i-3│ │ i-4│      │
                    │  └────┘ └────┘ └────┘ └────┘      │
                    │                                      │
  Low CPU           │  ┌────┐ ┌────┐                      │
  Scale in ──▶      │  │ i-1│ │ i-2│  ← back to desired  │
                    │  └────┘ └────┘                      │
                    └─────────────────────────────────────┘

  Min capacity  = minimum instances always running
  Desired       = how many instances ASG tries to maintain
  Max capacity  = maximum instances ASG can scale to
```

### ASG Scaling Policies

| Policy Type | How It Works | Use Case |
|-------------|-------------|----------|
| **Target Tracking** | Maintain a target metric (e.g., CPU at 50%) | Most common, simplest |
| **Step Scaling** | Add/remove instances in steps based on alarm severity | Fine-grained control |
| **Scheduled** | Scale at specific times | Predictable traffic patterns |
| **Predictive** | ML-based, predicts traffic and pre-scales | Recurring patterns |

### Manual Steps: Create an Auto Scaling Group

**Step 1: Create a Launch Template**

A launch template defines what kind of instances the ASG should create.

```bash
# Create a launch template
aws ec2 create-launch-template \
  --launch-template-name web-server-template \
  --version-description "v1" \
  --launch-template-data '{
    "ImageId": "ami-0c55b159cbfafe1f0",
    "InstanceType": "t3.micro",
    "KeyName": "my-app-key",
    "SecurityGroupIds": ["sg-0a1b2c3d4e5f67890"],
    "UserData": "'$(base64 -w0 userdata.sh)'",
    "TagSpecifications": [{
      "ResourceType": "instance",
      "Tags": [{"Key": "Name", "Value": "ASG-WebServer"}]
    }]
  }'
```

**Expected Output:**
```json
{
    "LaunchTemplate": {
        "LaunchTemplateId": "lt-0abcd1234efgh5678",
        "LaunchTemplateName": "web-server-template",
        "DefaultVersionNumber": 1
    }
}
```

**Step 2: Create the Auto Scaling Group**

```bash
aws autoscaling create-auto-scaling-group \
  --auto-scaling-group-name web-asg \
  --launch-template LaunchTemplateId=lt-0abcd1234efgh5678,Version='$Latest' \
  --min-size 2 \
  --max-size 6 \
  --desired-capacity 2 \
  --vpc-zone-identifier "subnet-aaa111,subnet-bbb222" \
  --target-group-arns $TG_ARN \
  --health-check-type ELB \
  --health-check-grace-period 300 \
  --tags Key=Environment,Value=production,PropagateAtLaunch=true
```

**Command Breakdown:**
| Flag | Meaning |
|------|---------|
| `--min-size 2` | Always keep at least 2 instances |
| `--max-size 6` | Never exceed 6 instances |
| `--desired-capacity 2` | Start with 2 instances |
| `--vpc-zone-identifier` | Subnets to launch instances in (multi-AZ) |
| `--target-group-arns` | Connect to ALB target group |
| `--health-check-type ELB` | Use ALB health checks (not just EC2 status) |
| `--health-check-grace-period 300` | Wait 5 min before checking new instances |

**Step 3: Add a Scaling Policy (Target Tracking)**

```bash
# Scale based on average CPU — ASG adds/removes instances to keep CPU at ~50%
aws autoscaling put-scaling-policy \
  --auto-scaling-group-name web-asg \
  --policy-name cpu-target-tracking \
  --policy-type TargetTrackingScaling \
  --target-tracking-configuration '{
    "PredefinedMetricSpecification": {
      "PredefinedMetricType": "ASGAverageCPUUtilization"
    },
    "TargetValue": 50.0,
    "ScaleInCooldown": 300,
    "ScaleOutCooldown": 60
  }'
```

**Step 4: Add a Scheduled Scaling Action (optional)**

```bash
# Scale up to 4 instances every weekday at 8 AM UTC
aws autoscaling put-scheduled-update-group-action \
  --auto-scaling-group-name web-asg \
  --scheduled-action-name scale-up-morning \
  --recurrence "0 8 * * MON-FRI" \
  --desired-capacity 4

# Scale down to 2 instances every weekday at 8 PM UTC
aws autoscaling put-scheduled-update-group-action \
  --auto-scaling-group-name web-asg \
  --scheduled-action-name scale-down-evening \
  --recurrence "0 20 * * MON-FRI" \
  --desired-capacity 2
```

**Step 5: Monitor the ASG**

```bash
# Check ASG status
aws autoscaling describe-auto-scaling-groups \
  --auto-scaling-group-names web-asg \
  --query 'AutoScalingGroups[0].{
    Min:MinSize,Max:MaxSize,Desired:DesiredCapacity,
    Instances:Instances[].{ID:InstanceId,Health:HealthStatus,AZ:AvailabilityZone}
  }'

# Check scaling activities (scale in/out events)
aws autoscaling describe-scaling-activities \
  --auto-scaling-group-name web-asg \
  --query 'Activities[0:5].{Time:StartTime,Status:StatusCode,Cause:Cause}' \
  --output table
```

### What Happens When an Instance Fails in ASG

```
1. Instance i-3 fails health check
2. ALB stops sending traffic to i-3 (round robin skips it)
3. ASG detects unhealthy instance
4. ASG terminates i-3
5. ASG launches a new instance i-5 to maintain desired capacity
6. New instance passes health check
7. ALB adds i-5 back to round robin rotation

Timeline:
  t=0    i-3 fails health check
  t=30s  ALB marks i-3 as unhealthy, stops routing to it
  t=60s  ASG terminates i-3
  t=90s  ASG launches i-5
  t=5min i-5 passes health check, receives traffic
```

### Manual Steps via AWS Console

1. Go to **EC2 → Launch Templates → Create Launch Template**
2. Configure: AMI, instance type, key pair, security group, user data
3. Go to **EC2 → Auto Scaling Groups → Create Auto Scaling Group**
4. Select the launch template

## 3.16 Placement Groups

Placement groups control how EC2 instances are placed on underlying hardware.

### Three Strategies

| Strategy | Description | Max Instances | Use Case |
|----------|-------------|---------------|----------|
| **Cluster** | All instances in same AZ, same rack | No limit | HPC, Big Data, low-latency networking (10 Gbps) |
| **Spread** | Each instance on different hardware | 7 per AZ per group | HA for individual instances |
| **Partition** | Instances spread across partitions (different racks) | 7 partitions per AZ, 100s of instances | HDFS, HBase, Cassandra, Kafka |

```
│ │EC││EC││EC│   │        │2 │    │2 │    │2 │        │ EC2 EC2 │  │ EC2 EC2 │
```

## 3.17 Elastic Network Interfaces (ENI)

An ENI is a virtual network card attached to an EC2 instance.

### ENI Attributes

- Primary private IPv4 + one or more secondary IPv4
- One Elastic IP per private IPv4
- One public IPv4
- One or more security groups
- A MAC address

### Key Properties

- ENIs are bound to a specific AZ
- You can create ENIs independently and attach/detach them from instances
- Moving an ENI between instances provides failover capability

```bash
# Create an ENI
ENI_ID=$(aws ec2 create-network-interface \
  --subnet-id subnet-0abc123 \
  --groups sg-0abc123 \
  --description "Failover ENI" \

  --network-interface-id $ENI_ID \
  --instance-id i-0abc123 \
  --device-index 1

# Detach and move to another instance for failover
ATTACHMENT_ID=$(aws ec2 describe-network-interfaces \
  --network-interface-ids $ENI_ID \
  --query 'NetworkInterfaces[0].Attachment.AttachmentId' --output text)

aws ec2 detach-network-interface --attachment-id $ATTACHMENT_ID
aws ec2 attach-network-interface \
  --network-interface-id $ENI_ID \
  --instance-id i-0def456 \
  --device-index 1
```

## 3.18 EC2 Hibernate

Hibernate preserves the in-memory (RAM) state of an instance. On resume, the instance boots much faster because the OS doesn't restart — RAM is restored from the root EBS volume.

### How It Works

```
Running ──▶ Hibernate ──▶ RAM dumped to encrypted root EBS ──▶ Stopped
Stopped ──▶ Start ──▶ RAM restored from EBS ──▶ Running (fast boot)
```

### Requirements

- Instance RAM must be < 150 GB
- Root volume must be EBS, encrypted, and large enough for RAM dump
- Supported families: C3-C5, M3-M5, R3-R5, T2, T3
- Cannot hibernate for more than 60 days
- Available for On-Demand, Reserved, and Spot instances

### Use Cases

- Long-running processing that you want to pause/resume
- Services with slow initialization (JVM warm-up, large caches)
- Saving RAM state between work sessions

```bash
# Enable hibernation at launch
aws ec2 run-instances \
  --image-id ami-0abcdef1234567890 \
  --instance-type m5.large \
  --hibernation-options Configured=true \
  --block-device-mappings '[{
    "DeviceName": "/dev/xvda",
    "Ebs": {"VolumeSize": 30, "Encrypted": true, "VolumeType": "gp3"}
  }]'

# Hibernate the instance
aws ec2 stop-instances --instance-ids i-0abc123 --hibernate

# Resume (just start it)
aws ec2 start-instances --instance-ids i-0abc123
```

## 3.19 EC2 Instance Store

EBS volumes are network drives — good but with latency. For maximum I/O performance, use EC2 Instance Store (physically attached disks).

| Feature | EBS | Instance Store |
|---------|-----|----------------|
| **Type** | Network-attached | Physically attached |
| **Persistence** | Persists after stop/terminate | Lost on stop/terminate (ephemeral) |
| **Performance** | Up to 256,000 IOPS (io2) | Millions of IOPS |
| **Use case** | Databases, boot volumes | Buffer, cache, scratch data, temp files |
| **Backup** | Snapshots | Your responsibility |

Instance store is available on specific instance types (i3, d2, h1, etc.).

```bash
# i3.xlarge has 1x 950 GB NVMe SSD instance store
aws ec2 run-instances \
  --image-id ami-0abcdef1234567890 \
  --instance-type i3.xlarge \
  --count 1

# After SSH, the instance store is available as /dev/nvme0n1
# You must format and mount it yourself
sudo mkfs.xfs /dev/nvme0n1
sudo mkdir /data
sudo mount /dev/nvme0n1 /data
```

## 3.20 EBS Volume Types

EBS volumes come in 6 types. Only SSD types (gp2/gp3/io1/io2) can be boot volumes.

### SSD Volumes

| Type | IOPS | Throughput | Size | Use Case |
|------|------|------------|------|----------|
| **gp3** | 3,000 baseline, up to 16,000 | 125 MiB/s, up to 1,000 MiB/s | 1 GiB–16 TiB | General purpose (recommended) |
| **gp2** | 3 IOPS/GiB, up to 16,000 | Up to 250 MiB/s | 1 GiB–16 TiB | General purpose (legacy) |
| **io2 Block Express** | Up to 256,000 | Up to 4,000 MiB/s | 4 GiB–64 TiB | Databases needing sub-ms latency |
| **io1** | Up to 64,000 (Nitro) | Up to 1,000 MiB/s | 4 GiB–16 TiB | Databases, sustained IOPS |

### HDD Volumes (cannot be boot volumes)

| Type | IOPS | Throughput | Size | Use Case |
|------|------|------------|------|----------|
| **st1** (Throughput Optimized) | Up to 500 | Up to 500 MiB/s | 125 GiB–16 TiB | Big Data, data warehouses, log processing |
| **sc1** (Cold HDD) | Up to 250 | Up to 250 MiB/s | 125 GiB–16 TiB | Infrequently accessed data, lowest cost |

### gp3 vs gp2

- **gp3**: IOPS and throughput are independent of size — you set them separately
- **gp2**: IOPS scales with size (3 IOPS per GiB). At 5,334 GiB you hit max 16,000 IOPS
- **gp3 is recommended** for new workloads — more predictable, often cheaper

### EBS Multi-Attach (io1/io2 only)

Attach the same EBS volume to multiple EC2 instances in the same AZ. Up to 16 instances. Requires cluster-aware filesystem (not XFS/EXT4).

Move snapshots to an archive tier that is 75% cheaper. Restore takes 24–72 hours.

### Recycle Bin for Snapshots

Protect against accidental deletion. Deleted snapshots go to a recycle bin and can be recovered.


### Fast Snapshot Restore (FSR)

Force full initialization of a snapshot so volumes created from it have no latency on first use. Expensive — use only for production databases.

## 3.22 Amazon EFS (Elastic File System)

EFS is a managed NFS that can be mounted on many EC2 instances across multiple AZs simultaneously.

### EBS vs EFS

| Feature | EBS | EFS |
|---------|-----|-----|
| **Attach** | One instance (except io1/io2 Multi-Attach) | 100s of instances across AZs |
| **AZ** | Locked to one AZ | Multi-AZ |
| **Protocol** | Block storage | NFS v4.1 |
| **OS** | Linux + Windows | Linux only (POSIX) |
| **Pricing** | Pay for provisioned size | Pay per use |
| **Cost** | Lower | ~3x gp2 (but with storage tiers) |

### EFS Performance Modes

| Mode | Latency | Throughput | Use Case |
|------|---------|------------|----------|
| **General Purpose** (default) | Low | Standard | Web servers, CMS, WordPress |
| **Max I/O** | Higher | Higher | Big data, media processing |

### EFS Throughput Modes

| Mode | How It Works |
|------|-------------|
| **Bursting** | Throughput scales with storage size |
| **Provisioned** | Set throughput independent of size |
| **Elastic** (recommended) | Auto-scales up to 3 GiB/s reads, 1 GiB/s writes |

### EFS Storage Classes

| Class | Access Pattern | Cost |
|-------|---------------|------|
| **Standard** | Frequently accessed | Full price |
| **Infrequent Access (IA)** | Accessed less often | Lower storage, retrieval fee |
| **Archive** | Rarely accessed (few times/year) | 50% cheaper than Standard |

Use lifecycle policies to move files between tiers automatically.

### Mount EFS on EC2

```bash
# Install EFS utilities
sudo yum install -y amazon-efs-utils

# Create mount point
sudo mkdir /efs

# Mount using EFS mount helper (recommended)
sudo mount -t efs fs-0abc1234:/ /efs

# Or mount with TLS encryption
sudo mount -t efs -o tls fs-0abc1234:/ /efs

# Add to /etc/fstab for persistent mount
echo "fs-0abc1234:/ /efs efs defaults,_netdev 0 0" | sudo tee -a /etc/fstab
```

### EBS Delete on Termination

By default, the root EBS volume is deleted when the instance terminates. Additional volumes are NOT deleted. Control this with `DeleteOnTermination` attribute.

```bash
# Check DeleteOnTermination setting for an instance's volumes
aws ec2 describe-instances --instance-ids i-0abcdef1234567890 \
  --query 'Reservations[].Instances[].BlockDeviceMappings[].{Device:DeviceName,DeleteOnTerm:Ebs.DeleteOnTermination,VolumeId:Ebs.VolumeId}' \
  --output table

# Expected output:
# ---------------------------------------------------------------
# |                    BlockDeviceMappings                       |
# +------------+------------------+-----------------------------+
# |   Device   | DeleteOnTerm     |          VolumeId           |
# +------------+------------------+-----------------------------+
# |  /dev/xvda |  True            |  vol-0abcdef1234567890      |
# |  /dev/sdf  |  False           |  vol-0fedcba0987654321      |
# +------------+------------------+-----------------------------+

# Modify to preserve root volume on termination
aws ec2 modify-instance-attribute --instance-id i-0abcdef1234567890 \
  --block-device-mappings '[{"DeviceName":"/dev/xvda","Ebs":{"DeleteOnTermination":false}}]'

# Set DeleteOnTermination at launch time
aws ec2 run-instances \
  --image-id ami-0abcdef1234567890 \
  --instance-type t3.micro \
  --block-device-mappings '[{"DeviceName":"/dev/xvda","Ebs":{"VolumeSize":20,"DeleteOnTermination":false}}]' \
  --min-count 1 --max-count 1
```

**Real-life use case:** A database team launches EC2 instances with EBS root volumes. They set `DeleteOnTermination=false` so that if someone accidentally terminates the instance, the root volume (containing custom configurations) is preserved for forensic analysis or data recovery.

## 3.26 EC2 Instance Connect & Recovery

### EC2 Instance Connect

Browser-based SSH — no need to manage SSH keys. Pushes a temporary SSH key to the instance metadata.

```bash
# Install EC2 Instance Connect on the instance (Amazon Linux 2)
sudo yum install ec2-instance-connect -y

# Use CLI to push a temporary key and SSH
aws ec2-instance-connect send-ssh-public-key \
  --instance-id i-0abcdef1234567890 \
  --instance-os-user ec2-user \
  --ssh-public-key file://~/.ssh/id_rsa.pub \

# Expected output:
# {
#   "RequestId": "abcdef12-3456-7890-abcd-ef1234567890",
#   "Success": true
# }

# Then SSH normally (key is valid for 60 seconds)
ssh ec2-user@10.0.1.50
```

**Security group requirement:** Inbound SSH (port 22) must be allowed from the EC2 Instance Connect IP range (`3.16.146.0/29` for us-east-1). For EC2 Instance Connect Endpoint (EIC Endpoint), no public IP or inbound rules needed — it creates a private tunnel.

```bash
# Create an EC2 Instance Connect Endpoint (for private instances)

aws ec2-instance-connect ssh \

```

### EC2 Instance Recovery

CloudWatch alarm can automatically recover an instance if it fails a status check. The recovered instance has the same instance ID, private IP, Elastic IP, and EBS volumes.

```bash
# Create a CloudWatch alarm that auto-recovers the instance on status check failure
aws cloudwatch put-metric-alarm \
  --alarm-name "EC2-AutoRecover-i-0abcdef1234567890" \
  --namespace AWS/EC2 \
  --metric-name StatusCheckFailed_System \
  --dimensions Name=InstanceId,Value=i-0abcdef1234567890 \
  --statistic Maximum \
  --period 60 \
  --evaluation-periods 2 \
  --threshold 1 \
  --comparison-operator GreaterThanOrEqualToThreshold \
  --alarm-actions arn:aws:automate:us-east-1:ec2:recover

# Expected output:
# (no output on success, exit code 0)

# Verify the alarm was created
aws cloudwatch describe-alarms --alarm-names "EC2-AutoRecover-i-0abcdef1234567890" \
  --query 'MetricAlarms[0].{Name:AlarmName,State:StateValue,Actions:AlarmActions}'

# Expected output:
# {
#   "Name": "EC2-AutoRecover-i-0abcdef1234567890",
#   "State": "OK",
#   "Actions": ["arn:aws:automate:us-east-1:ec2:recover"]
# }
```

**What's preserved after recovery:** Instance ID, private/public/Elastic IPs, EBS volumes, instance metadata, placement group. **What's lost:** In-memory data (RAM contents). Only works with EBS-backed instances (not instance store).

**Real-life use case:** A stateless web server behind an ALB has a recovery alarm. When the underlying hardware fails, AWS automatically migrates the instance to healthy hardware. The instance keeps its private IP, so the ALB target group doesn't need updating.

### Instance Scheduler

AWS Instance Scheduler is a solution that automates starting and stopping EC2 and RDS instances on a schedule to reduce costs.

```
┌──────────────────┐     ┌─────────────┐     ┌──────────────────┐
│ CloudWatch Event │────▶│   Lambda     │────▶│ EC2/RDS          │
│ (every 5 min)    │     │ (scheduler)  │     │ Start/Stop       │
└──────────────────┘     └──────┬───────┘     └──────────────────┘
                                │
                         ┌──────▼───────┐
                         │  DynamoDB    │
                         │ (schedules)  │
                         └──────────────┘
```

```bash
# Deploy Instance Scheduler via CloudFormation
aws cloudformation create-stack \
  --stack-name instance-scheduler \
  --template-url https://s3.amazonaws.com/solutions-reference/instance-scheduler-on-aws/latest/instance-scheduler-on-aws.template \
  --parameters ParameterKey=SchedulingActive,ParameterValue=Yes \
               ParameterKey=Regions,ParameterValue=us-east-1 \
               ParameterKey=DefaultTimezone,ParameterValue=America/New_York \
  --capabilities CAPABILITY_IAM

# Tag instances to apply a schedule
aws ec2 create-tags --resources i-0abcdef1234567890 \
  --tags Key=Schedule,Value=office-hours

# The scheduler Lambda checks tags every 5 minutes and starts/stops accordingly
# "office-hours" schedule: Mon-Fri 08:00-18:00 EST

# Create a custom schedule using the scheduler CLI
scheduler-cli create-schedule \
  --name office-hours \
  --periods "office-hours-period" \
  --timezone "America/New_York" \
  --stack instance-scheduler

scheduler-cli create-period \
  --name office-hours-period \
  --begintime 08:00 \
  --endtime 18:00 \
  --weekdays mon-fri \
  --stack instance-scheduler
```

**Real-life use case:** A company has 50 development EC2 instances that only need to run during business hours (Mon-Fri, 8am-6pm). Instance Scheduler stops them at 6pm and starts them at 8am, saving ~65% on EC2 costs for those instances ($50K+/year savings).

## 3.27 ELB — Advanced Features

### Sticky Sessions (Session Affinity)

Route a client to the same target for the duration of a session. Uses cookies.

| Cookie Type | Name | Duration |
|------------|------|----------|
| **Application-based** (custom) | Custom name | Set by app |
| **Application-based** (ALB) | AWSALBAPP | Set by ALB |
| **Duration-based** | AWSALB (ALB) / AWSELB (CLB) | 1s–7 days |

```bash
# Enable duration-based sticky sessions on a target group
aws elbv2 modify-target-group-attributes \
  --target-group-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/my-tg/abcdef \
  --attributes Key=stickiness.enabled,Value=true \
               Key=stickiness.type,Value=lb_cookie \
               Key=stickiness.lb_cookie.duration_seconds,Value=3600

# Enable application-based sticky sessions
aws elbv2 modify-target-group-attributes \
  --target-group-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/my-tg/abcdef \
  --attributes Key=stickiness.enabled,Value=true \
               Key=stickiness.type,Value=app_cookie \
               Key=stickiness.app_cookie.cookie_name,Value=JSESSIONID

# Verify stickiness settings
aws elbv2 describe-target-group-attributes \
  --target-group-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/my-tg/abcdef \
  --query 'Attributes[?starts_with(Key,`stickiness`)]'

# Expected output:
# [
#   {"Key": "stickiness.enabled", "Value": "true"},
#   {"Key": "stickiness.type", "Value": "lb_cookie"},
#   {"Key": "stickiness.lb_cookie.duration_seconds", "Value": "3600"}
# ]
```

**Real-life use case:** A legacy Java application stores session data in memory (not in Redis/DynamoDB). Sticky sessions ensure a user's requests always go to the same instance so their session isn't lost. The trade-off: uneven load distribution if some sessions are long-lived.

### Cross-Zone Load Balancing

Distributes traffic evenly across all registered targets in all AZs.

| LB Type | Default | Cross-AZ Charges |
|---------|---------|-----------------|
| ALB | Always on | No charge |
| NLB | Disabled | Charges apply |
| CLB | Disabled | No charge |

### Connection Draining (Deregistration Delay)

Time to complete in-flight requests when a target is deregistered or unhealthy. Default: 300 seconds. Set to 0 to disable.

```bash
# Set deregistration delay to 30 seconds (for fast-draining apps)
aws elbv2 modify-target-group-attributes \
  --target-group-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/my-tg/abcdef \
  --attributes Key=deregistration_delay.timeout_seconds,Value=30

# Disable connection draining entirely
aws elbv2 modify-target-group-attributes \
  --target-group-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/my-tg/abcdef \
  --attributes Key=deregistration_delay.timeout_seconds,Value=0

# Check current setting
aws elbv2 describe-target-group-attributes \
  --target-group-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/my-tg/abcdef \
  --query 'Attributes[?Key==`deregistration_delay.timeout_seconds`]'
# Expected output:
# [{"Key": "deregistration_delay.timeout_seconds", "Value": "30"}]
```

**Real-life use case:** During a rolling deployment, ASG deregisters old instances. With a 30-second draining period, in-flight API requests complete before the instance is terminated. For WebSocket apps, set a longer timeout (e.g., 3600 seconds).

### Connection Idle Timeout

Maximum time a connection can be idle before the load balancer closes it. Default: 60 seconds for ALB.

```bash
# Set idle timeout to 120 seconds (for long-polling or slow APIs)
aws elbv2 modify-load-balancer-attributes \
  --load-balancer-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:loadbalancer/app/my-alb/abcdef \
  --attributes Key=idle_timeout.timeout_seconds,Value=120

# For WebSocket connections, increase to 3600
aws elbv2 modify-load-balancer-attributes \
  --load-balancer-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:loadbalancer/app/my-alb/abcdef \
  --attributes Key=idle_timeout.timeout_seconds,Value=3600
```

**Important:** Your application's keep-alive timeout must be greater than the ALB idle timeout. If the app closes the connection before the ALB, clients get 502 errors.

### SSL/TLS — Server Name Indication (SNI)

SNI allows loading multiple SSL certificates on one load balancer. The client indicates which hostname it's connecting to, and the LB selects the right certificate.

- ALB: Supports SNI (multiple certs)
- NLB: Supports SNI
- CLB: Does NOT support SNI (one cert only)

### ALB Listener Rules

ALB routes requests based on listener rules evaluated in priority order. Each rule has conditions and actions.

```bash
# Create a path-based routing rule
aws elbv2 create-rule \
  --listener-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:listener/app/my-alb/abcdef/1234567890 \
  --priority 10 \
  --conditions '[{"Field":"path-pattern","Values":["/api/*"]}]' \
  --actions '[{"Type":"forward","TargetGroupArn":"arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/api-tg/abcdef"}]'

# Create a host-based routing rule
aws elbv2 create-rule \
  --listener-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:listener/app/my-alb/abcdef/1234567890 \
  --priority 20 \
  --conditions '[{"Field":"host-header","Values":["api.example.com"]}]' \
  --actions '[{"Type":"forward","TargetGroupArn":"arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/api-tg/abcdef"}]'

# Create a rule with multiple conditions (host + path)
aws elbv2 create-rule \
  --listener-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:listener/app/my-alb/abcdef/1234567890 \
  --priority 5 \
  --conditions '[
    {"Field":"host-header","Values":["admin.example.com"]},
    {"Field":"path-pattern","Values":["/dashboard/*"]}
  ]' \
  --actions '[{"Type":"forward","TargetGroupArn":"arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/admin-tg/abcdef"}]'

# Create a redirect rule (HTTP → HTTPS)
aws elbv2 create-rule \
  --listener-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:listener/app/my-alb/abcdef/http-listener \
  --priority 1 \
  --conditions '[{"Field":"path-pattern","Values":["/*"]}]' \
  --actions '[{"Type":"redirect","RedirectConfig":{"Protocol":"HTTPS","Port":"443","StatusCode":"HTTP_301"}}]'

# Create a fixed response rule (maintenance page)
aws elbv2 create-rule \
  --listener-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:listener/app/my-alb/abcdef/1234567890 \
  --priority 1 \
  --conditions '[{"Field":"path-pattern","Values":["/maintenance"]}]' \
  --actions '[{"Type":"fixed-response","FixedResponseConfig":{"StatusCode":"503","ContentType":"text/html","MessageBody":"<h1>Under Maintenance</h1>"}}]'

# List all rules for a listener
aws elbv2 describe-rules \
  --listener-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:listener/app/my-alb/abcdef/1234567890 \
  --query 'Rules[].{Priority:Priority,Conditions:Conditions[0].Field,Actions:Actions[0].Type}'
```

**Rule condition types:** `host-header`, `path-pattern`, `http-header`, `http-request-method`, `query-string`, `source-ip`.

### Target Group Weighting (Weighted Target Groups)

Route traffic to multiple target groups with different weights. Used for blue/green deployments and canary releases.

```bash
# Forward action with weighted target groups (90% blue, 10% green)
aws elbv2 modify-rule \
  --rule-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:listener-rule/app/my-alb/abcdef/1234567890/rule123 \
  --actions '[{
    "Type": "forward",
    "ForwardConfig": {
      "TargetGroups": [
        {"TargetGroupArn": "arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/blue-tg/abcdef", "Weight": 90},
        {"TargetGroupArn": "arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/green-tg/abcdef", "Weight": 10}
      ],
      "TargetGroupStickinessConfig": {"Enabled": true, "DurationSeconds": 300}
    }
  }]'

# Shift to 50/50 for testing
# Then shift to 0/100 to complete the deployment
```

**Real-life use case:** During a canary deployment, 5% of traffic goes to the new version. If error rates stay low, gradually increase to 25%, 50%, then 100%. If errors spike, shift back to 0% on the new version instantly.

### Preserving Client IP

Different load balancers handle client IP preservation differently:

| LB Type | Client IP Visible? | How to Get Client IP |
|---------|-------------------|---------------------|
| CLB (HTTP) | No | `X-Forwarded-For` header |
| ALB | No | `X-Forwarded-For` header |
| NLB (instance target) | Yes | Direct from packet |
| NLB (IP target) | No | Proxy Protocol v2 |

```bash
# Enable Proxy Protocol v2 on NLB target group (for IP targets)
aws elbv2 modify-target-group-attributes \
  --target-group-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/my-nlb-tg/abcdef \
  --attributes Key=proxy_protocol_v2.enabled,Value=true

# For ALB, the client IP is in X-Forwarded-For header
# Nginx config to log the real client IP:
# set_real_ip_from 10.0.0.0/8;
# real_ip_header X-Forwarded-For;

# Verify X-Forwarded-For is being sent (from target instance)
curl -s http://localhost/headers
# {
#   "X-Forwarded-For": "203.0.113.50",
#   "X-Forwarded-Port": "443",
#   "X-Forwarded-Proto": "https"
# }
```

### Network Load Balancer (NLB) Details

- Layer 4 (TCP, UDP, TLS)
- Millions of requests per second, ultra-low latency
- One static IP per AZ (supports Elastic IP)
- Target types: EC2 instances, IP addresses, ALB
- Health checks: TCP, HTTP, HTTPS
- No security groups on NLB — traffic passes through to targets

### Gateway Load Balancer (GWLB)

Layer 3 (IP) load balancer for deploying and scaling third-party network virtual appliances (firewalls, IDS/IPS, deep packet inspection).

```
                    ┌─────────────────────────────────────────┐
                    │           Security VPC                   │
Internet ──▶ GWLB ─┤  ┌──────────┐  ┌──────────┐            │
  │         Endpoint│  │ Firewall │  │ Firewall │            │
  │                 │  │ Instance │  │ Instance │            │
  │                 │  └──────────┘  └──────────┘            │
  │                 └─────────────────────────────────────────┘
  │                           │ (inspected traffic)
  ▼                           ▼
Application VPC ◀─────────────┘
```

- Uses GENEVE protocol on port 6081
- Target types: EC2 instances, IP addresses
- Use case: Route all traffic through firewalls before reaching your application

```bash
# Create a Gateway Load Balancer
aws elbv2 create-load-balancer \
  --name my-gwlb \
  --type gateway \
  --subnets subnet-0abcdef1234567890 subnet-0fedcba0987654321

# Expected output:
# {
#   "LoadBalancers": [{
#     "LoadBalancerArn": "arn:aws:elasticloadbalancing:us-east-1:123456789012:loadbalancer/gwy/my-gwlb/abcdef",
#     "Type": "gateway",
#     "State": {"Code": "provisioning"}
#   }]
# }

# Create a target group for firewall appliances
aws elbv2 create-target-group \
  --name firewall-targets \
  --protocol GENEVE \
  --port 6081 \
  --vpc-id vpc-0abcdef1234567890 \
  --target-type instance \
  --health-check-protocol HTTP \
  --health-check-port 80

# Register firewall instances
aws elbv2 register-targets \
  --target-group-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/firewall-targets/abcdef \
  --targets Id=i-0abcdef1234567890 Id=i-0fedcba0987654321

# Create a GWLB endpoint service
aws ec2 create-vpc-endpoint-service-configuration \
  --gateway-load-balancer-arns arn:aws:elasticloadbalancing:us-east-1:123456789012:loadbalancer/gwy/my-gwlb/abcdef \
  --acceptance-required

# Create GWLB endpoint in the application VPC
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-app \
  --vpc-endpoint-type GatewayLoadBalancer \
  --service-name com.amazonaws.vpce.us-east-1.vpce-svc-0abcdef \
  --subnet-ids subnet-app
```

**Real-life use case:** A regulated financial institution routes all ingress traffic through Palo Alto firewalls deployed behind a GWLB. The GWLB scales the firewall fleet automatically and distributes traffic using 5-tuple hash for flow stickiness.

### Load Balancing across Peered VPCs

ALB/NLB can target instances in peered VPCs using IP target type.

```bash
# Register targets in a peered VPC (use IP target type)
aws elbv2 register-targets \
  --target-group-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/cross-vpc-tg/abcdef \
  --targets Id=10.1.1.50,Port=8080 Id=10.1.2.50,Port=8080

# The target group must use target-type=ip (not instance)
# VPC peering must be established and route tables configured
```

### Load Balancing across On-Premises

NLB/ALB can target on-premises servers using IP target type over Direct Connect or VPN.

```bash
# Register on-premises servers as targets (via Direct Connect/VPN)
aws elbv2 register-targets \
  --target-group-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/onprem-tg/abcdef \
  --targets Id=192.168.1.100,Port=8080,AvailabilityZone=all \
            Id=192.168.1.101,Port=8080,AvailabilityZone=all

# AvailabilityZone=all is required for targets outside the VPC
```

Kubernetes controller that provisions ALB (for Ingress) and NLB (for Service type LoadBalancer) automatically.

```bash
# Install AWS Load Balancer Controller on EKS
helm repo add eks https://aws.github.io/eks-charts

```

## 3.28 Key Takeaways

1. Choose instance types based on workload (t3 for dev, c5 for compute, r5 for memory, g5/p5 for GPU)
2. Always use key pairs + security groups (never open port 22 to 0.0.0.0/0 in production)
3. Use IAM roles instead of access keys on EC2 instances
4. Use user data for automated bootstrapping
5. Take EBS snapshots regularly for backups
6. Use `file -s` to check a disk before formatting — avoid data loss
7. To resize EBS: modify volume in AWS → growpart → resize2fs/xfs_growfs
8. Use Spot instances for fault-tolerant workloads (up to 90% savings)
9. Use Reserved Instances or Savings Plans for steady-state production workloads
10. Stopped instances still cost money (EBS volumes)
11. Use ALB + ASG for high availability — ALB distributes traffic via round robin, ASG replaces failed instances
12. Placement Groups: Cluster for HPC, Spread for HA, Partition for distributed systems
13. EBS gp3 is recommended over gp2 — independent IOPS/throughput settings
14. Use EFS when multiple instances need shared file access across AZs
15. EC2 Instance Store for maximum I/O — but data is ephemeral
16. Use EC2 Hibernate to preserve RAM state for faster restarts
17. Use IMDSv2 (token-based) for instance metadata — protects against SSRF
